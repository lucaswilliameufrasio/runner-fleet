# Decisões de implementação

1. **REST + webhooks na primeira versão.** Escopos por repo e org, registro tradicional efêmero, labels cumulativas e grupos. O cliente oficial `actions/scaleset` é alternativa para escala maior, não uma segunda implementação concorrente. Não validamos Scale Sets em GitHub real neste ambiente.
2. **Monólito Go + SPA SvelteKit.** Um banco SQLite local, WAL e transações para reservas/comandos. Não exige Node ou Kubernetes na execução do servidor.
3. **mTLS direto no Go.** Nginx stream passa TLS do hostname de agentes; não aceitar certificado por header arbitrário. Rotação de certificado individual com sobreposição de duas identidades e revogação no banco.
4. **Capacidade antes de efeitos externos.** Slots reservados precedem inscrição e criação. Ociosos também consomem orçamento. Estado desconhecido mantém reserva. GitHub faz matching e não permite pin de job por nosso coordenador.
5. **Containers efêmeros para código confiável.** Base rootless sem host mounts. CPU/RAM via runtime; disco reservado/monitorado, quota rígida por filesystem fora do suporte atual. Nenhum cache local compartilhado entre jobs; workflows podem usar actions/cache no GitHub.
6. **Docker isolado por job opt-in.** Sidecar Docker privilegiado apenas em máquina dedicada e dentro de Docker rootless. Volume/socket privados por instância, rede compartilhada. Compatibilidade e segurança operacional dependem do canário; não é fronteira de VM para código hostil.
7. **Drain via GitHub.** Remover registro somente se API permitir e, depois, parar listener local. Em indisponibilidade de API, aguardar; nunca matar job com base apenas em um heartbeat antigo.
8. **Criptografia de backups.** Argon2id + AES-GCM, formato versionado, VACUUM INTO, upload S3 verificado por HEAD antes de retenção. Recovery kit fora do banco é obrigatório. Senhas não ficam em texto no SQLite.
9. **Migração conservadora.** Patches somente em destinos estáticos validados pelo parser. Não reformatar arquivo inteiro nem usar regex em matrizes/expressões. SHA atual deve coincidir antes de PR.
10. **Distribuição assinada.** Ed25519 protege manifestos; checksum verifica binários. Chave de assinatura fica fora do pacote; a confiança inicial pode ser fixada antes de bootstrap.
11. **Workers EC2 Spot gerenciados pelo Fleet.** Pool pode escolher workers EC2 efêmeros junto ou em vez de máquinas fixas. O control plane cria/ajusta/encerra instâncias Spot com operações idempotentes e reconciliação persistente; a identidade AWS vem do provider chain do SDK, nunca de segredo no browser/SQLite. Operador fornece região, AMI, subnets, security groups e instance profile. Cada pool escolhe bootstrap em Ubuntu/Debian ou AMI pré-configurada, e Spot-only ou fallback On-Demand explícito com tipos permitidos. O agente consulta aviso de interrupção via IMDSv2 e sinaliza drain ao control plane; jobs ativos podem ser encerrados pela AWS antes de concluir. Não criar VPC/IAM nem fazer fallback de custo sem configuração explícita.
12. **Isolamento e falha de capacidade Spot.** Worker cloud começa dedicado a um único pool, com slots e limites calculados da configuração e capacidade real do tipo EC2. Falta de Spot sem fallback deixa capacidade indisponível/job na fila; erros ambíguos de criação são reconciliados pelo client token/tag antes de nova tentativa. Interrupção é best-effort: parar novos jobs e drenar runners ociosos, sem afirmar que um job ativo sobreviverá ao reclaim. Revisitar após canário multi-AZ e evidência de execução real.
13. **O Fleet administra todos os runners da instalação, não só containers efêmeros.** Status: aceito. Data: 2026-11-02. Uma máquina cadastrada pode oferecer pool de container, pool de serviço persistente, ou os dois, e o pool ainda pode somar workers EC2 Spot. Spot continua sendo fonte de máquina. O modo padrão segue o item 5: container efêmero, imagem por digest, Docker rootless. O modo serviço baixa o `actions/runner` oficial, confere o checksum da arquitetura e registra com `config.sh` sem `--ephemeral`, no usuário de sistema `fleet-runner` (shell nologin, sem sudo e fora de `sudo`/`admin`/`wheel`/`docker`). O agente não recebe sudo: a unit tem `NoNewPrivileges`, então um helper root separado observa um diretório que o agente pode escrever. CPU e memória viram `CPUQuota` e `MemoryMax`. Disco continua reserva. O scheduler mantém os ociosos até `min` e a fila e pede drain do excedente. O preparo apt/rpm/zypper entra no `install.sh`, usado pelo comando, pelo SSH e pelo user-data Spot. O SSH aceita root, `sudo -n` ou `su -`; a senha de root existe só na requisição. O registro deste corte é GitHub. A CLI `actions-runner-host` continua o preparo avulso, sem control plane e sem registrar o agent.

Alternativas rejeitadas: sudo a partir do processo do agente; aplicar nologin ao `fleet-agent`, que precisa de shell para o Docker rootless; tratar `CPUQuota` como fronteira de VM; implementar o runner do Gitea neste corte. Revisitar o registro Gitea quando houver um binário e um fluxo de inscrição próprios. Revisitar o isolamento se o job passar a ser código não confiável.

Skills utilizadas nesta entrega: openai-library:library para persistência do pacote. Nenhuma skill externa de terceiros foi invocada; o plano pede aplicar instruções disponíveis, sem exigir um repositório de skills particular.
